01

请求延迟

按客户端时间线计算。t0为发送前计时起点，t1为首个有效输出，tn为最后有效输出，t_end为流式采集结束。

计时符号与边界
使用同一客户端单调时钟计算时间差
符号含义
t_plan负载策略给出的计划提交时刻
t_admit调度器准入、获准占槽的时刻
t0JSON序列化和HTTP请求构造完成后、实际发送前的计时起点
t1 / tn客户端解析出首个 / 最后一个非空有效输出事件的时刻；Chat含思考与正文
t_end有效流式采集结束时刻：Completions必须收到[DONE]；当前Chat路径也可能在正常EOF结束（分阶段仍要求finish_reason=stop）
t_close响应排空与关闭完成、允许释放请求槽的时刻，可晚于t_end
T正式调度启动至正式样本收集返回的实际秒数，不含预热
N / M实际输出Token数 / 非空有效流式事件数
01

TTFT

首次有效输出等待时间，从实际发送前计时到客户端解析出首个非空有效输出；Chat包含思考与正文。

TTFT = t1 − t0
单位
ms
统计对象
成功请求，每请求一个值，等权聚合
有效条件
存在有效输出事件
  • 包含t0之后实际发生的连接池等待、建连、网络、服务排队、推理与解析；t0之前的调度等待和请求构造另计。
  • Completions取choices[0].text中的非空字符串；Chat取choices[0].delta中的reasoning、reasoning_content或content非空字符串。同一事件同时包含思考与正文时只计时一次；reasoning与reasoning_content同时非空时必须内容一致，否则采集失败，思考字段类型非法也失败。响应头、首字节、空角色事件、心跳、仅usage事件与[DONE]均不是首个有效输出。
  • 只有思考输出的Chat响应仍可成功，has_content=false；首个非空正文延迟另存first_content_latency_ms，无正文时为null。工具调用字段不作为有效输出；完全没有有效输出属于采集失败，不能将TTFT补0。客户端TTFT与Engine内部TTFT分开比较。
  • 整体TTFT取首个非空思考或正文事件；thinking_metrics开关不改变整体公式。分阶段思考TTFT、首正文延迟及资格条件见第41—48项。
计算示例

示例数据：同一请求的实际计时起点t0=0ms，首个非空有效输出事件t1=400ms。时间均相对t0表示。

  1. 先选定起点：JSON序列化和HTTP请求构造完成后、实际发送前，记为t0。
  2. 再选定终点：客户端解析出首个非空有效输出（Chat含思考与正文）的时刻，记为t1；响应头、空角色事件和心跳不作为终点。
  3. 用终点减去起点，得到首次有效输出等待时间。
    TTFT = t1 − t0 = 400 − 0 = 400ms

t0之前的计划等待与请求构造不计入TTFT；t0之后实际发生的连接池等待、建连、网络、服务排队、推理和客户端解析均可能计入。在线客户端TTFT与Engine内部TTFT应分别比较。

TPOT

包含首Token等待的平均输出耗时，截止最后有效输出，再除以实际输出Token数。

TPOT = (tn − t0) / N
单位
ms/token
统计对象
可计算的成功请求，按N加权
有效条件
N>0；正常路径需最后输出时间，缺失时回退E2EL/N
  • 当前LuBan-Meter报告TPOT包含TTFT；它与排除首Token等待的请求级平均ITL不同。
  • 最后输出之后的usage、结束标记等尾部采集不加入正常路径的分子。旧记录缺少last_output_latency_ms时兼容回退为E2EL/N，回退值直接参与TPOT加权聚合；当前结果没有单独的回退标记或回退计数，复核时需检查原始记录。此时ITL不可用，配置了tpot约束的SLO无法判定。
  • 缺输出usage时不可计算，不能用max_tokens代替N。N=1时仍可计算TPOT。
  • 本条整体TPOT覆盖全部输出，与仅计算加权均值的thinking TPOT分开。最后输出时间缺失时，当前计算器用E2EL/N回退，ITL不因此补值。
计算示例

示例数据：同一请求t0=0ms，最后有效输出tn=1300ms，实际输出Token数N=10；采集结束t_end=1500ms。

  1. 取从实际计时起点到最后有效输出的总时间，包含首Token等待。
    输出时间 = tn − t0 = 1300 − 0 = 1300ms
  2. 从服务返回的usage读取实际输出Token数，分母为10，不使用max_tokens或流式事件数。
    N = 10token
  3. 用上述总时间除以实际输出Token数。
    TPOT = (tn − t0) / N = 1300 / 10 = 130ms/token

这是当前LuBan-Meter报告中包含TTFT的TPOT口径。1300ms之后到1500ms的尾部采集不进入本例分子。若旧记录缺少最后输出时间，兼容计算会退回E2EL/N并进入同一TPOT聚合，当前无单独回退标记或计数；需检查原始记录识别。此时ITL不可用，配置了tpot约束的SLO归为无法判定。缺少实际N时不能计算，不能把N补为0。

请求级平均ITL

排除首次输出等待的请求级平均Token间隔，使用首末有效输出之间的时间。

平均ITL = (tn − t1) / (N − 1)
单位
ms/token
统计对象
可计算且N>1的成功请求，按N−1加权
有效条件
N>1，首末有效输出时间可用
  • N=1时没有后续Token间隔，ITL不可用，不补0，也不进入ITL加权分布。
  • 一个事件可包含多个Token。若M=1且N>1，首末事件时间相同会使平均ITL为0，但不代表模型内部逐Token生成没有耗时。Chat的t1、tn覆盖思考和正文，N沿用服务报告的输出总数。
  • ITL的P99是请求级平均值的Token间隔加权分位数，不能称为全部真实逐Token间隔的P99。
  • 逐轮itl_ms_by_turn已沿用本条定义和N−1权重，独立于逐轮事件间隔；见第49项。
计算示例

示例数据：同一请求首个有效输出t1=400ms，最后有效输出tn=1300ms，实际输出Token数N=10。

  1. 先扣除首次有效输出之前的等待，仅保留首末有效输出之间的时间。
    后续输出时间 = tn − t1 = 1300 − 400 = 900ms
  2. 10个Token对应9个相邻Token间隔，因此分母为N−1。
    间隔权重 = N − 1 = 10 − 1 = 9
  3. 总后续输出时间除以间隔数，得到请求级平均ITL。
    ITL = (tn − t1) / (N − 1) = 900 / 9 = 100ms/token

要求实际N>1，且首末输出时间可用。N=1时没有后续Token间隔，ITL不可计算。此值是请求级平均量；客户端只观察到分块事件时，不能据此恢复每个Token的真实到达时间。

Stream Event ITL

相邻非空有效流式事件的观测时间差，用于观察客户端流式输出是否出现较长停顿。

事件间隔Δe_k = e_k − e_(k−1)，k=2…M
单位
ms
统计对象
汇集成功请求的全部事件间隔，每间隔等权
有效条件
每请求M>1才产生间隔样本
  • 一条请求贡献M−1个事件间隔；M=1不贡献间隔样本。首次输出之前的等待不进入该列表。
  • 单位是ms，不能在未知每事件Token数时标为ms/token。多Token合并、推测解码或流式分块策略都会影响事件间隔分布。
  • 事件时间是客户端解析后观测时间，不是服务端每个Token的生成时间。Chat的事件列表合并非空思考与正文事件，同一事件含两个通道时只计一次。
计算示例

示例数据：客户端观察到3个非空有效输出事件，时刻依次为400、700、1300ms；实际输出Token总数为10。

  1. 对相邻有效事件分别做时间差，不把首事件到t0的等待加入事件间隔列表。
    间隔1 = 700 − 400 = 300ms 间隔2 = 1300 − 700 = 600ms
  2. M=3个事件只产生M−1=2个间隔样本。
    间隔列表 = [300, 600]ms；样本数 = 3 − 1 = 2
  3. 求两个事件间隔的算术平均。
    事件间隔均值 = (300 + 600) / 2 = 450ms

一个事件可能携带多个Token，450ms是事件间隔均值，不能标作450ms/token。Case聚合会合并成功请求中的有效事件间隔样本；每条请求贡献的间隔数可以不同。

E2EL

从实际发送前到有效流式采集结束的端到端请求延迟。

E2EL = t_end − t0
单位
ms
统计对象
成功请求，每请求一个值，等权聚合
有效条件
请求成功且采集结束
  • t_end为采集器成功返回时刻；Chat在有有效输出后可由[DONE]或正常EOF结束，Completions必须收到[DONE]，否则请求失败。t_end可能晚于最后有效输出tn。
  • tn之后、t_end之前的尾部采集计入E2EL。t_end之后的响应排空和关闭不计入E2EL，但仍可能占槽并延长Case窗口。
  • 仅响应排空或关闭失败时，记录connection_cleanup_error，不改写已有效生成请求的成功状态。
计算示例

示例数据：t0=0ms，最后有效输出tn=1300ms，流式采集结束t_end=1500ms，响应排空与关闭完成t_close=1600ms。

  1. 确定采集结束边界：Chat有有效输出后可由[DONE]或正常EOF结束；Completions必须收到[DONE]，只有正常HTTP EOF而无该标记仍失败。Chat的EOF不自动补造finish_reason=stop，分阶段仍按实际结束原因判断。
  2. 从该结束时刻减去请求实际计时起点。
    E2EL = t_end − t0 = 1500 − 0 = 1500ms
  3. 把尾部采集和关闭耗时分开列出，避免错误改变E2EL终点。
    尾部采集 = 1500 − 1300 = 200ms，已计入E2EL 采集后的排空与关闭 = 1600 − 1500 = 100ms，未计入E2EL

响应排空和关闭虽然晚于E2EL的终点，仍可能占用客户端执行槽，并延长正式Case统计窗口。因此E2EL、最后输出时间和槽位释放时间应分别保存。

Dispatch Delay

请求从计划提交时刻到实际发送前计时起点的滞后。

Dispatch Delay = t0 − t_plan
单位
ms
统计对象
已进入处理的成功与失败请求，等权聚合
有效条件
计划时刻与实际计时起点均已记录
  • 该值能显露压测客户端因准入等待、本地执行或请求构造而落后于计划的情况。
  • 调度器scheduling_delay_s=t_admit−t_plan，终点是准入；dispatch_delay_ms的终点是t0，二者不能仅换算单位后互换。
计算示例

示例数据：以实际计时起点为0ms，请求计划时刻t_plan=−300ms，调度器准入t_admit=−100ms，实际计时起点t0=0ms。负数仅表示发生在t0之前。

  1. 计算计划时刻到调度器准入的等待。
    准入延迟 = t_admit − t_plan = −100 − (−300) = 200ms
  2. 计算准入后到请求实际计时起点的额外时间。
    准入至计时起点 = t0 − t_admit = 0 − (−100) = 100ms
  3. Dispatch Delay覆盖以上两段，直接用t0减去计划时刻。
    Dispatch Delay = t0 − t_plan = 0 − (−300) = 300ms 核对：200 + 100 = 300ms

调度器scheduling_delay_s对应准入延迟，本例为0.2s；在线dispatch_delay_ms对应300ms。二者结束边界不同，不能仅换算单位后互相替代。

Scheduled Latency

从计划提交时刻到采集结束，包含实际开始之前的等待。

Scheduled Latency = 处理结束时刻 − t_plan 成功请求：Scheduled Latency = Dispatch Delay + E2EL
单位
ms
统计对象
有完整时间记录的成功与失败请求，等权聚合
有效条件
计划时刻与处理结束时刻均已记录
  • 成功请求以采集结束为终点；失败记录以失败处理结束为终点。失败记录不应混入成功请求的TTFT或E2EL分布。
  • 需要衡量从计划时刻开始的总等待时，不能只使用TTFT。该指标仍不加入采集结束之后的响应收尾。
计算示例

示例数据：请求计划时刻t_plan=−300ms，实际计时起点t0=0ms，流式采集结束t_end=1500ms。

  1. 先计算计划时刻到实际计时起点的Dispatch Delay。
    Dispatch Delay = 0 − (−300) = 300ms
  2. 再计算实际计时起点到采集结束的E2EL。
    E2EL = 1500 − 0 = 1500ms
  3. 将两段相加，或直接以采集结束减去计划时刻。
    Scheduled Latency = t_end − t_plan = 1500 − (−300) = 1800ms = Dispatch Delay + E2EL = 300 + 1500 = 1800ms

该指标反映从计划时刻开始的等待，能显露客户端实际开始请求的滞后。它仍以采集结束为终点，不额外加入t_end之后的响应关闭时间。

实际Token计数

实际输入和输出Token数，是Token延迟、吞吐量及加权聚合的计数依据。

I = usage.prompt_tokens N = usage.completion_tokens
单位
token
统计对象
成功请求中实际可用的usage计数
有效条件
服务返回相应实际计数
  • 目标输入长度、max_tokens、输出预算和SSE事件数都不能替代实际Token数。相同随机种子也不保证不同工具产生相同请求文本。
  • 整个usage缺失或为null时，只要有效输出与采集正常，仍可保留成功状态与已测延迟；输入、输出计数均为null，缺失输出N的请求不进入TPOT、ITL和依赖N的速度统计。
  • 成功请求缺少某类计数时，对应Case完整Token总量与吞吐量为不可用，不能把部分已知总量当作全量，也不能把缺失填0。

总体标准差

总体标准差，表示指标值围绕均值的离散程度，单位与原指标相同。

总体标准差σ = √[Σ(x_i−μ)² / n] 加权总体标准差σ_w = √[Σw_i(x_i−μ_w)² / Σw_i]
单位
沿用原指标单位
统计对象
普通分布等权；TPOT/ITL沿用各自权重
有效条件
至少一个有效值
  • 当前采用总体方差，分母为n或总权重，不使用样本标准差的n−1。
  • 多数请求毫秒字段与统计结果保留3位小数；逐请求排队事实保留原始精度，其分布和均值保留6位小数。thinking TPOT/ITL仅有加权均值，不生成分位数或标准差。复算需考虑各字段舍入精度。
计算示例

示例数据：8个等权示例值为[10,10,10,10,30,30,30,30]ms；本图说明普通分布的总体标准差。

  1. 先求8个值的算术平均。
    均值μ = (4 × 10 + 4 × 30) / 8 = 160 / 8 = 20ms
  2. 每个值减去均值后再平方，并把8项相加。
    平方偏差和 = 4 × (10 − 20)² + 4 × (30 − 20)² = 4 × 100 + 4 × 100 = 800ms²
  3. 除以总体个数8得到方差，再开平方回到毫秒单位。
    总体方差 = 800 / 8 = 100ms² 总体标准差σ = √100 = 10ms

当前使用总体标准差，分母为n=8；若改用样本标准差的n−1=7，会得到约10.690ms，不能混用。TPOT/ITL的加权标准差另按Σw(x−μ)²/Σw计算。

单位
req/s
