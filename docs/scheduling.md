# 定时计划架构

`schedule`在原有运行链路前登记、排队和触发整份配置，不属于请求级Profile或
SchedulingStrategy；不改变Benchmark、Metric和Case的执行或计时接口。

- `core/schedule_commands.py`负责登记、修改、取消与列表；复用`build_plan`
  静态校验，保存完整已解析参数，文件引用保留绝对路径。参数快照独立于原JSON，
  运行中不修改。入口不加载模型或调用服务。
- `core/schedule_time.py`保存创建时的IANA时区，以带UTC偏移的ISO时间比较到期
  条件，使用croniter计算五字段cron的未来时间。日与星期同时受限时采用OR。
  一次性本地时间若不存在则拒绝，若存在夏令时歧义则要求提供明确UTC偏移。
- `core/schedule_store.py`是计划和执行状态的唯一持久化入口。当前工作目录下
  `schedule/YYYY-MM-DD/plans.json`保存完整计划修订及参数快照，
  `executions.csv`追加状态事实和结果摘要；每日目录按记录发生的本机日期生成，
  每日目录固定包含两个文件，当日执行引用的参数快照也保存在该日JSON。
  全局递增sequence保持跨天及系统时钟回拨后的
  更新顺序；执行引用具体plan_revision，旧参数保持可追溯。无另外的计划数据库。
- JSON以原子替换保存，CSV追加后flush/fsync；共享文件锁串行保护读取、修改、
  入队和领取。先持久化执行再推进下次时间，避免中途退出丢失已到期任务；按
  计划ID及原计划时间去重，恢复重测用新的执行ID并通过retry_of关联。
- `core/scheduled_runs.py`持有项目服务锁，扫描到期计划并维护持久FIFO。每个
  项目最多运行一份配置；不同计划到点排队，同一计划已有未完成轮次则跳过后续
  触发。只有已启动运行的实际窗口参与原有指标，排队等待不进入Case/Run窗口。
- `runtime/schedule_worker.py`是独立进程入口，持有项目运行锁，再检查领取状态，
  用现有`RunCoordinator`启动任务子进程、整理结果并生成HTML。执行及任务子进程
  共享同一实例日志。result.json补充计划ID、执行ID、原计划时间、重测关系及
  脱敏参数快照；调度层只汇总状态和Case计数，不重新计算模型性能指标。
- 取消先持久化计划禁用状态，再移除队列或通过停止标记请求当前运行中断，避免
  取消后重启复活。修改与领取在同一存储锁下判定，启动中/运行中拒绝修改。
  日历变更使旧排队项失效；仅改参数时领取最新快照并保留原队列位置，即使修改
  命令在JSON保存后、CSV更新前退出，调度器也能据此修复，不会丢失待执行项。
- 恢复先使旧领取失效，通知旧进程停止，等待运行锁释放后核对完整结果：已完成
  的收尾，不完整的从头生成新运行。新重测优先于保留队列；未入队的停机过期
  轮次跳过。晚到的旧进程会因领取失效退出，不能启动旧参数并与新运行重叠。

`tests/test_schedule.py`验证日历边界、跨天记录与快照、FIFO、过期和更新取消；
`tests/test_schedule_processes.py`使用本地测试Benchmark实际启动CLI、调度、协调器
和任务进程，覆盖串行排队、修改取消、服务SIGKILL后的重测恢复、统一日志及失败
继续队列。它们不构成真实模型、GPU、Windows或Linux开机自启验证。
